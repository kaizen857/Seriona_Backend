Implementation notes:
- reconcileRoot() still performs serial discoverScannerPaths() enumeration and prepares AudioReconcileTask values in that discovered order.
- WorkerTask submission remains through ScannerWorkerPool from task 18.
- After workerPool.waitAll(), reconcileRoot() now explicitly stable-sorts WorkerResult values by their matching AudioReconcileTask index before converting successes into result.songs.
- runScan() publishes FileScanned from rootResult.songs and builds the final PlaylistTreeBuilder snapshot from allSongs, so both event order and snapshot song node order now consume the same sorted success order.
- Worker errors are still collected via workerPool.errorsSnapshot() before success publication, and workerResult.error entries are skipped without blocking successful songs.
- Task 20 was not implemented: cachedSongByPath()/audioTaskByPath() remain linear lookups; no unordered_map cache lookup was added.

Focused coverage:
- Added CTest alias: seriona.scanner.event_ordering -> seriona_scanner_service_tests --test-case="scanner service publishes worker results in discovered file order".
- The focused test creates 01-first.flac and 02-second.flac, blocks the first metadata read, waits until the second read has entered, releases the first, and asserts FileScanned event order plus snapshot node song order remain first then second.
- Added songsInPublishedOrder() because the existing songsIn() helper sorts by path and cannot prove raw snapshot publication order.
- Broad scanner regression exposed scanner_worker_pool_config_tests.cpp relying on result vector positions while its failing task was selected by concurrent read count. That test now binds failure to broken.flac and asserts results by path, removing an ordering assumption that conflicts with this task's contract.

Failing-first / baseline notes:
- Pre-implementation focused alias unexpectedly passed: ctest --test-dir build -R 'seriona.scanner.event_ordering' --output-on-failure returned 100% passed before the orchestrator sort.
- Readback of ScannerWorkerPool::waitAll() showed the reason: it currently waits for all futures, then gets futures in pending-container order. That makes the current worker pool accidentally preserve submission order, so the new characterization cannot fail until waitAll() collection behavior changes.
- The product fix is still necessary because task 18 evidence called out the implicit dependency. The orchestrator now owns the order guarantee explicitly instead of relying on ScannerWorkerPool internals.
