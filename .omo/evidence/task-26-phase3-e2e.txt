Defect exposed and fixed:
- Initial e2e run failed even though playlist state was correct. V3 sidecar persistence logged `failed to record scanner scan-root state: step done: UNIQUE constraint failed: locations.file_path`, and the sidecar still retained the deleted path.
- Root cause: `SQLiteCacheV3::upsertLocation()` only handled `ON CONFLICT(location_id)`. When a file changed, `computeLocationId(path, size, mtime)` produced a new location_id for the same file_path, so the unique `locations.file_path` constraint blocked the replacement and prevented later prune state from persisting.
- Fix: `SQLiteCacheV3::upsertLocation()` now removes any existing row with the same file_path but a different location_id inside the writer transaction before the existing upsert. `tests/scanner/scanner_cache_v3_locations_tests.cpp` now locks this replacement contract.
