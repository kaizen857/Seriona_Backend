# Scanner 性能对比报告

本报告基于 task-27、task-28、task-30 的证据文件整理，目标是把“当前实现、并发收益、增量收益、剩余差距”讲清楚。

## 证据来源

- `task-27-perf-report.md`：1000 / 5000 / 10000 songs 的冷扫、热扫、增量扫实测。
- `task-28-tagreader-stress.txt`：TagReader 并发安全性证据形态，含 TSAN 结果和 helgrind 超时记录。
- `task-30-config-tuning.txt`：扫描配置可调、环境变量覆盖和串行 fallback 行为。

## 结论先行

- 当前实现已经具备缓存命中、增量扫描、并发 worker、串行 fallback 和可调并发这些能力。
- 但 task-27 的实测仍明显没有达到架构文档里写的理想目标，尤其是 5000 / 10000 songs 场景。
- task-28 证明的是线程安全形态，不是“8 或 16 就该成为生产默认值”的性能证明。
- task-30 只是把并发度做成可配置，并补上串行退化路径，它本身不会制造速度提升。

## 当前实现 vs 优化后

### 当前实现

task-27 的实测结果表明，当前实现已经能稳定区分冷扫、热扫和增量扫，但总体耗时仍然偏高。

| songs | 冷扫 scanner wall | 热扫 scanner wall | 增量扫 scanner wall | 观察 |
| ---: | ---: | ---: | ---: | --- |
| 1000 | 2695 ms | 2707 ms | 2715 ms | 已接近秒级，但不代表大库可接受 |
| 5000 | 67927 ms | 69075 ms | 69890 ms | 明显高于理想冷扫 < 30 秒 |
| 10000 | 291309 ms | 293764 ms | 317402 ms | 明显高于理想冷扫 < 30 秒 |

### 优化后目标

`docs/optimal-scanner-architecture.md` 里 Phase 4 的目标仍是：

- 热扫描 < 5 秒
- 冷扫描 < 30 秒

把两者对齐后可以看出，当前实测还没有达到这个目标，尤其是 5000 / 10000 songs 的热扫和增量扫。

## 串行 vs 并发

task-28 的 TSAN 压测表明，TagReader 并发入口在 1 / 2 / 4 / 8 / 16 这些档位上都没有暴露线程竞争，`max_active_reads` 也与设定值一致或接近一致。这个结论说明并发通路本身可用。

但这不等于“更高并发一定更快”。task-28 只提供线程安全证据形态，没有证明 8 或 16 是正确的生产吞吐默认值。文档里仍应保留保守默认 4，直到有真实库吞吐证据支持上调。

task-30 还补了 `SERIONA_SCANNER_DISABLE_CONCURRENCY=1` 的串行 fallback。它的价值是可诊断、可退化、可控，不是性能提升来源。

## Full vs Incremental

task-27 的增量扫描在 benchmark 形状里只处理 2 个 changed files，cache hit rate 也接近 100%。这说明增量路径的工作量确实更小，但 wall time 仍然没有降到理想目标。

| songs | Full hot | Incremental | cache hit |
| ---: | ---: | ---: | ---: |
| 1000 | 2707 ms | 2715 ms | 100.00% / 99.80% |
| 5000 | 69075 ms | 69890 ms | 100.00% / 99.96% |
| 10000 | 293764 ms | 317402 ms | 100.00% / 99.98% |

这里要直说两个事实：

1. Incremental 的逻辑形态是对的，确实只处理很少的变化文件。
2. 但 task-27 观察到的 wall time 仍然被目录遍历、结果汇总和其他阶段成本主导，所以它没有自然落到“应该很快”的直觉区间。

## 观测到的差距

- 1000 songs 已经是秒级，但没有形成“热扫 < 5 秒”的压力优势。
- 5000 songs 的冷扫、热扫和增量扫都明显超过理想目标。
- 10000 songs 的增量扫甚至比热扫更慢，这说明当前瓶颈不是单纯的 TagReader 并发。

## 约束与 caveats

- task 27 使用的是 synthetic fixtures 和 fake metadata seam，适合验证扫描形态和统计，不适合当成真实媒体吞吐结论。
- task 28 证明的是 TSAN/thread-safety 形态，不证明 8 / 16 是合适的生产默认吞吐值。
- task 30 增加的是可配置性和串行 fallback，不会自动带来速度提升。
- 当前数据没有达到理想目标，这不是文档措辞问题，而是实测结果本身。

## 后续判断

如果后续要继续压缩时间，优先看 task-27 中 phase 1、结果聚合和增量路径的实际开销，而不是只继续提高 TagReader 并发上限。
