## 0. 结论摘要

1. **当前「用户自定义分隔符」是一个根本性的错配**：它实现的是「某个第三方工具合并双语时临时发明的产物」，而不是「格式的约定」。调研证实：**没有任何主流平台在服务端用分隔符存双语歌词**——网易云、QQ、酷狗、Musixmatch 都返回两个独立字段（`lrc`/`tlyric`、`lyric`/`trans`），Apple Music TTML 用 `<translation for="L1">` 按行 key 引用，Navidrome/OpenSubsonic 用 `kind="translation"` + `lang` 的平级轨道。所有分隔符都是客户端/第三方工具自己发明的，且互不兼容。
2. **用户的原始思路（按语言/脚本切分）在真实曲库上成立且效果极好**。当前语料 1,616 个 LRC / 66,080 行（原 2,978 / 122,307 行；`独立歌词` 目录经授权删除，其中 1,265 个为曲库他处的逐字节副本），经七轮修正后：**60,397 条对照行上不一致为 0（判定精确率 100.00%）**、覆盖率 99.96%、保守放弃仅 **27 行（0.04%）**；**弱约定（纯空白）子集覆盖率 97.8%**；**「切点落在括号内」72 行、译文残留分隔符 127 行、反斜杠约定文件的 31 行错切均已清零**；**用户四轮标注全部通过**（139+19+4+4 行级「正确」逐字节保持、2+22+88+116 行级「错误」全部修好、41/41 显式期望值精确命中、文件级 33/33 保持）；**护栏盲区（无 ` / ` 标注 5,530 行，无客观 oracle）已如实披露**（§6.6、§6.2.6、§6.2.7）。护栏 + 复核工具已落地并跑通。
3. **决定性发现：歧义必须在「歌曲级」消解，不能逐行赌**。逐行决策时，「单空格」这类弱信号的假阳率高达 32.38%；改为「先从整首的聚合证据推断本文件的切分约定，再按该约定逐行应用」后，误判率降至接近 0。这一点由用户提出，是本方案成立的关键。
4. **不需要任何语言识别（LID）库**（结论经五轮修正后依然成立——所有修正都不是「识别得更准」，而是「不再对显式证据过度设防」、以及「不切开配对括号」）。ICU **不提供**语言识别（`ucsdet_getLanguage` 对 UTF-8 输入直接不返回语言）；而 `UScriptRun` 不在 ICU 公开头文件中（需自写约 40 行，可参考 ICU `extra/scrptrun`、Godot、Calibre 的成熟实现）。所有 LID 库在 10–60 字短句上都不可靠，且新增依赖在三端供给上代价高昂（唯一进 vcpkg 的 CLD3 默认要求 ≥140 字节，对本场景等于「直接拒答」）。
5. **「汉字↔汉字不可区分」这一结论已被推翻**（D30）。Han 确实被中日韩共享，但当作者写出了 ` / ` 分隔符时，脚本证据**不应**成为门槛——旧算法对强分隔符也要求脚本证据，人为造出了「盲区」。用户二轮复核判定 39 条此类行为「应切分」；修正后该类别从 **248 行降到 1 行**（§3.3.3、§6.2.2）。
6. **切分是懒惰的**（用户决策）：只在播放某曲时才切分并缓存，缓存携带产出时所用的目标语言；目标语言变更时已算过的曲目废弃重算、**未算过的无需任何处理**。因此启动、扫描与切换目标语言**均零等待**，且全库无需遍历。
7. **同时间戳双行（参照行）纳入本次范围**，并在调研中发现一个**会静默破坏它的既有实现缺陷**：后端 `lrc_parser.cpp:165-171` 与 TagReader `TextNormalize.cpp:225-235` 都按 `(timestamp, text)` **非稳定排序**，会把同一时间戳的多行按文本重排，破坏「第一行 = 原文」所依赖的文件顺序（§8.8）。
8. **顺带发现 8 处 LRC 解析器缺口**（§8.9），其中 `[offset:]` 标签**被解析但从不应用**（带 offset 的歌词整首时间轴偏移错误）与上述非稳定排序属**静默正确性缺陷**；另有增强 LRC 逐字标签未剥离、unsynced 歌词整首丢弃、仅支持 `.lrc` 单一扩展名。
9. **不做数据库迁移**（用户决策）：schema 直接改、`user_version` 3→4，旧库在点击「恢复播放列表」时拒绝。但**现有链路会给出误导性消息**（显示「播放控制器已停止」而非「数据库不兼容」），需配套修正方能兑现该意图（§8.10）。

## 1. 需求与背景

### 1.1 用户原述问题

应用当前让用户自定义「歌词分隔符」来切分同时存储原文与译文的 LRC 行。用户认为这个做法**不优雅**，且会引入**意想不到的 bug**：

- 分隔符本身含空格时，原文内部的空格会被误当分隔；
- 原文内部含 `/` 等符号时会被误分割。

而根因是：**LRC 标准中没有规定双语如何存储**，导致「分隔符」形态多样：

- `原文 / 译文`（` / ` 两侧带空格）——占用户曲库的多数；
- `原文 译文`（单个空格）；
- 甚至「译文直接接在原文后面，连空格都没有」。

用户的思路是：**能否用算法识别一行里存在两种不同语言，从而自动切出「原文」与「译文」**，例如 `日文 / 中文`、`日文/中文`、`日文 中文`、甚至 `日文中文`（无分隔）都能正确划分。

用户也预见到原文自身可能是多语言混合的，例如：

```
haf en synk/.（ハンドシェイク受領、好意を返送） / 握手已接收，回赠善意
```

这里 ` / ` 左侧是原文，而原文本身又分两部分：`haf en synk/.` 是塔语（Hymmnos，《魔塔大陆》的人造语言），其后的括号是日文释义。

### 1.2 需求总结（由本文档归纳，经用户确认）

| # | 需求 |
|---|---|
| R1 | 移除用户可见的「歌词分隔符」配置；改为**自动划分** |
| R2 | 译文的目标语言**可由用户配置**（默认中文） |
| R3 | 自动划分无法保证 100% 正确，须提供**纠错渠道**，且纠错**必须持久化进数据库** |
| R4 | 纠错的语义是**内容寻址的覆盖缓存**：同一输入被纠正过，下次**直接复用纠正结果、不再跑算法** |
| R5 | 纠错粒度是**单行**（自然覆盖单首歌），因此**不能放在设置里** |
| R6 | 划分为**纯函数**：`f(行文本, 目标语言) → (原文, 译文, 置信度)` |
| R7 | 译文 = **最后一个语言段**（行尾中文算译文）；但代码须留**内部扩展点**，将来可改为可变位置，改动局部化 |
| R8 | **同一语言的注音/振假名必须排除**，不得当作译文（硬性） |
| R9 | `「」` 等成对符号**不作为容器语义**：作为普通字符，归属其所包裹的内容 |
| R10 | 常见分隔符可作**候选切分点**，但必须防止其「在译文中以普通字符出现」时被误当分界 |
| R11 | 性能与优雅优先；**允许破坏性修改**，只要不影响无关功能 |

### 1.3 已排除的方向（含理由）

- **❌ 按字符串内容判断语言后分别使用不同 collator / 分别调用不同语言的 LID**：会破坏严格弱序或产生不确定输出，且对短句不可靠。**绝对禁止**。
- **❌ 硬编码「含汉字即中文」**：实测会大量误判日文汉字。
- **❌ 依赖 LID 模型**：见 §5.4 与 §0.4。

## 2. 现状分析：当前实现与缺陷根因

### 2.1 歌词数据通路（磁盘 → 屏幕）

```
音频文件 + 同名 .lrc sidecar
  │
  ├─ TagReader：内嵌标签解析 → RawLyrics{timedLines, text}
  │    → NormalizeLyrics() → MusicTag::lyrics() = Lyrics(vector<Lyric>)
  │       （微秒时间戳 + 单条文本，无语言概念）
  │
  └─ 后端扫描器：expectedLyricsSidecarPath() + parseLrcFile() → LrcParseResult
       → effectiveLyrics（LyricLine{毫秒, text}）+ effectiveLyricsSource
         （None / EmbeddedTag / ExternalLrc）
       → SQLite 缓存：locations(lyrics_source, external_lrc_*) + lyrics(...)
       → PlaylistTreeSnapshot（SongMetadata.effectiveLyrics）
       → 控制层 PlayerStateSnapshot / LibraryStateSnapshot
       → 前端 AppFacade → LyricsModel::applyPlayerStateSnapshot()
            → Line{milliseconds, QString text}   ← 单条原始字符串，无语言信息
            → displayLine() / translationLine() 用用户分隔符表切分  ← 全栈唯一分割点
            → lines() / data() 角色 → QML ListModel → Text 元素
```

**关键事实：原文/译文的划分在整个技术栈中只存在于前端 `LyricsModel`。** 上游任何一级（TagReader、后端）都**不**检测、标注、切分或存储分离的原文/译文。每一行到达时都是单条不透明的 `text`。

### 2.3 缺陷根因

现有设计的缺陷不在于「分隔符选得不好」，而在于**把「作者的书写约定」当成了「用户的配置项」**：

1. **语义错位**：分隔符是**歌词文件作者**的书写习惯，不是**用户**的偏好。让用户为每个文件手动配置，等于把作者的自由度转嫁成用户的负担。
2. **无优先级与验证**：`earliestDelimiterHit` 取「最早出现」，一旦分隔符（如 ` / `）在原文中先于真正的分界出现，就必然切错。实测存在明确反例：`Rrha num wa ene revm /  / 我做了一个梦`（连续两个 ` / `）与 `（Afterburner） / 揺るぎない Spirit / （Afterburner） / 坚定不移的Spirit`（原文内含 ` / `），当前实现都会切在第一个 ` / `。
3. **弱信号无一致性背书**：若用户把「单个空格」配为分隔符，实测用户曲库中**6,055 行**的日文歌词内部空格会被误割；若配「全角空格 `　`」，则有 **13,266 行**被误割（全角空格在日文里是排版间距，不是分界）。
4. **配置与内容耦合**：同一曲库混用多种约定（实测 38 个文件在同一文件内混用 ` / ` 与 `｜`/`|`），单一全局配置在原理上无法覆盖。

### 3.3.1 关于「汉字 → 汉字」盲区的**精确界定**（含一处此前的表述错误）

**此前本文档举的两个例子是错的**。`我将咏唱一首连接大家与理想的诗` 与 `大地啊，即便裸露着肌肤` **确实都是中文**，把它们当作「无法区分」的例证是不成立的表述。

盲区的**真实形态**是：**纯汉字书写的日文**（日语汉字词）与**纯汉字书写的中文**相对。实测真实样本（` / ` 两侧均为纯汉字、且两侧文本不同）共 **279 行**：

```
言葉        / 这句话          ← 左侧日语汉字词，右侧简体中文
矛盾        / 这矛盾
一途        / 这执着
色形（色形） / 颜色
梔子        / 栀子花
絕望 喪失 別離 / 体味绝望 在失去中别离     ← 左繁体，右简体
模様（模様）  / 图案
一度        / 再一次
```

**★ 新发现：简体专有字信号可破解其中一部分**

「简体中文专有字形」（如 `这/们/门/语/谁/谢/时/机/爱/远`）在日文与繁体中文中**都不使用**，因此可作强证据。实测在 279 行中：

| 结果 | 行数 | 占全部歌词行 |
|---|---|---|
| 两侧完全相同（切分无意义） | 29 | — |
| **可用「右侧含简体专有字、左侧不含」判定** | **118** | **0.09%** |
| **仍不可判定（真盲区）** | **132** | **0.10%** |

即：盲区被压缩到 **0.10%**（原估 1.7% 中，属于「汉字↔汉字」的那部分几乎全部可解）。

**★ 但该信号当前【不纳入】主干算法，理由是工程可行性而非价值**：

构表过程**两次失败**，已作为证据记录：
1. 第一版把日文新字体与简体**同形**的字（`万`、`体`、`国`、`会`、`学`、`台`、`旧`、`状`、`独`…）误当「简体专有」，导致 `森羅/森罗` 被误判为「两侧都是简体」；
2. 第二版修补时又把简体字表整个塞进了排除集，导致简体专有字集**空集**。

结论：**该字表必须由 Unicode/CLDR 等权威数据源派生，不能手工枚举**。纳入前需要先解决「数据源从哪来、如何维护、跨 Unicode 版本如何更新」三个问题。已记为待决项（§13.2 Q-P6）。

### 3.3.2 「简体专有字」的实测收益（若将来纳入）

纳入后可直接判定的样例：`言葉 / 这句话`、`森羅！森羅！(万象！万象！) / 森罗！森罗！（万象！万象！）`、`粉雪 / 细雪`、`永遠... / （直到）永远...`、`絕望 喪失 別離 / 体味绝望 在失去中别离`（左繁右简）。

### 3.3.3 ★ 结论反转：「汉字↔汉字」盲区在实践中几乎不存在

上文的 279 行盲区统计是**用旧算法的受理条件**量的，而那个条件本身就是错的：它对**强分隔符**也要求「左侧必须有另一种语言的脚本证据」，于是大量真实存在的切分被拒。

用户第二轮的 120 条人工复核（§6.2.2）中，**39 条**此类行被判定为「应当切分」——这些行的作者**已经写出了 ` / ` 分隔符**，脚本证据在此不应成为门槛。

修正后（D30）实测：

| 指标 | 修正前 | 修正后 |
|---|---|---|
| 复核清单「『汉字→汉字』且两侧不同」类别 | 248 行 | **1 行** |
| 全库不一致行数 | 98 | **0**（三轮累计，§6.6） |

**因此 P6（是否纳入「简体专有字」字表）的优先级大幅下降**——它原本是为了破解这个「盲区」，而该盲区现在已被证明主要是过度验证造成的假象。目前仅剩 1 行残留在复核清单里。

## 4. 核心技术约束（原理性）

### 4.1 Han 被中日韩共享 → 纯汉字无法区分中日

Unicode 的 `Script` 属性把汉字统一为 `Han`（`Hani`）。日文的书写系统是 **Han + Hiragana + Katakana（+ 少量 Latin）**；韩文是 Hangul +（可选）Han。

- **决定性特征**：日文 = 「含假名」；韩文 = 「含谚文」。
- **纯 Han 文本**：Unicode **无法**告知这是中文还是日文汉字。这是**原理性上限**，不是工具不行。

→ **纯汉字的日文**（如 `言葉`、`矛盾`、`一途`、`色形`）与**纯汉字的中文**（如 `这句话`、`这矛盾`）在脚本层面完全同类，Unicode 无法区分。这是**原理性上限**，不是工具不行。

**但**：实测该盲区极小（279 行，占全部歌词行 **0.20%**），且其中 **118 行**可用「简体专有字」信号破解（§3.3.1），真正不可判定的仅 **132 行 = 0.10%**。

**注意表述**：不能说「中文和日文无法区分」——中文與日文在含假名时**极易区分**（假名是日文决定性特征）。只有**双方都用纯汉字书写**时才不可判定。

### 4.2 `Script` vs `Script_Extensions`

- `Script`：每个码点**单个**主脚本值。
- `Script_Extensions`：每个码点一个**脚本集合**，描述「常与多个脚本共用、但限于可枚举小集合」的字符。

例：`U+30FC`（长音符 `ー`）`Script=Common`、`scx={Hira,Kana}`；`U+3001`（`、`）`scx={Bopo,Hang,Hani,Hira,Kana,Mong,Yiii}`。

**含义**：日语标点、长音符、括号等「中性」字符的 `scx` 同时含中日韩脚本，**不能**用于判定语种，只能作「黏附到相邻强脚本段」的黏合剂。

### 4.3 ICU 的相关能力与边界

| 能力 | 结论 |
|---|---|
| 脚本查询 | `uscript_getScript( UChar32, UErrorCode* )`、`uscript_getScriptExtensions(...)`、`uscript_hasScript(...)`，均在现有 `ICU::uc` 中 |
| **语言识别** | **ICU 不提供**。`ucsdet_getLanguage` 是字符集检测的副产物，官方头文件明确写「**no language is identified for UTF-8 input data**」且「should not be used if robust, reliable language detection is required」。**本场景全是 UTF-8，此路径完全不可用** |
| **`UScriptRun`** | **不在公开头文件中**。C API 位于 `source/common/usc_impl.h`（内部头，不随 ICU 安装发布）；另有参考实现 `source/extra/scrptrun/`（`extra/`，**不编进 ICU 库**）。→ 需**自写约 40 行**，或移植 `scrptrun` 的 `ParenStack` 思路 |
| BreakIterator | 对中日泰等自动启用词典分词；`getRuleStatus()` 可辅助；**非线程安全**（每线程独立实例）。但它**不判语种**，也不解决纯 Han 中日同形问题 → 本方案**不用** |

**工业界佐证**：Godot 的 `modules/text_server_adv/script_iterator.cpp` 文件头明写「derived from ICU: icu4c/source/extra/scrptrun/scrptrun.cpp」；Calibre 用 `at_script_boundary()` 把 `Common/Invalid/Inherited` 视为不产生边界，并用 `iterator_language_for_script()` 把脚本映射到 locale（**把 Han 硬映射成 `zh`** —— 恰好暴露了纯 Han 无法区分中日）。

### 4.4 构造语言（conlang）与未知脚本

用户曲库含**塔语（Hymmnos）**（Ar tonelico 系列的人造语言），其罗马字转写（如 `haf en synk`）`Script = Latin`。

**实测占比（勿夸大）：46 个 LRC 文件 = 全部文件的 1.54%；1,747 行 = 全部歌词行的 1.26%**（另有「左侧含拉丁」的行 18,631 条，其中塔语来源仅 249 条，其余为罗马字日语/英语等）。即塔语是**小而特殊**的一类，不是主要数据。

- 任何通用 LID **都不支持** Hymmnos。
- LID 会**强行**在拉丁语系里挑一个语言，且**不会**给出「未知」——这是最危险的「自信地错」。

→ **正确策略**：把「拉丁段但无法确认语言」「未知脚本」「私用区」一律标为 **unknown**，**绝不**用它判定原/译；系统应保留其内容为**原文候选**，把决定权交给「另一位是已知目标语言」的规则。**永远不要因为识别不出就丢内容。**

**★ 塔语带来的一个具体算法教训（已修正）**

塔语歌词常以**多个空格做视觉对齐**（如 `PARADIGM SHIFT  ━━ 「范式迁移……」`、`cenjue innna ,     cenjue ciel —— 「…」`）。若把 `"  "`（双空格）列为候选约定且优先级高于 `" "`，就会**抢先匹配到作者的对齐空格**，把 `━━` 误判进译文：

```
错误（双空格优先）：原文 `PARADIGM SHIFT`  /  译文 `━━ 「范式迁移——（改变这世界的标准）」`
正确（移除双空格后）：原文 `PARADIGM SHIFT  ━━` / 译文 `「范式迁移——（改变这世界的标准）」`
```

**修正**：**从候选中移除双空格**。理由：双空格边界在任何情况下也都是单空格边界，而单空格配合「最左 + 严格验证」会落到正确的括注边界（且译文常被括号整体包裹，此时括号区起点优先于任何空白，见 §6.2.1/§6.2.4）；把双空格列入纯属有害。该结论由回归工具直接发现（§6.6）。

### 4.5 性能与线程

- 算法是**纯函数**、无 I/O、无状态；每行只做一次 O(n) 扫描（n ≈ 10–60 码点）。
- `UCollator`（排序所需的）非线程安全，既有实现已用 `thread_local`；本算法若仅用 `uscript_getScript`（无状态纯函数）则**无线程问题**。

## 5. 外部调研

### 5.1 LRC 格式自身

- **无标准组织**。Wikipedia 信息框写明 **Developed by: None**，Open/Free format。这就是所有混乱的根源。
- **A2 扩展（Enhanced LRC）与翻译无关**：它由 A2 Media Player 引入，用**尖括号** `<mm:ss.xx>` 标注**逐字**时间戳。
- **元数据标签**：`ti/ar/al/au/lr/length/by/offset/re/tool/ve/#`。**没有任何表示「翻译」的标签**（否定证据：Wikipedia 标签表中不存在 `[tr:]`、`[language:]` 等）。
- **多时间戳行**是真实存在的（副歌复用）：`[00:10.28][01:25.09][02:28.25]喜羊羊`。
- **`offset`**：全局时间偏移（毫秒，带正负号）。
- **「unsynced」不是 LRC 语法概念**（Wikipedia 页无此节）。它是工具侧概念，有三种互不相同含义：①无时间戳纯文本但仍用 `.lrc` 后缀；②LRCLIB 的 `plainLyrics` 字段；③库内部 synced→unsynced 降级类型。

### 5.6 学术现状：**这是一个空白**

- OpenAlex 检索 `lyrics translation alignment`、`bilingual lyrics split`、`bilingual text segmentation`：**无任何**解决「双语歌词行→原文/译文切分」的成果。
- 检索到的「lyric alignment」文献几乎全部是**音频↔文本的时间对齐**（phoneme/word-level alignment，如 `schufo/lyrics-aligner`、ICASSP 2024 的实时对齐），**与原文/译文划分无关**。引用时**必须**说清这个区别，否则是范畴错误。
- 真正做「歌词翻译」的两篇（EMNLP 2023 Findings `10.18653/v1/2023.findings-emnlp.3`、EMNLP 2024 Findings `10.18653/v1/2024.findings-emnlp.315`）做的是**机器翻译生成**（旋律约束下生成译文），**不是**从已有双语文本中分离。
- 最接近的学术脉络是 **code-switching LID**（2014/2016 共享任务及后续神经模型），但它们做「逐词语种标注」且**依赖标注语料训练**，属重方案。

→ **本问题的正确解法是「产品启发式 + 运行级语族分类」，而不是既有算法的直接套用。** 这一点应在设计文档中如实写明。

### 6.1 原型迭代（关键教训）

| 版本 | 思路 | 结果 | 教训 |
|---|---|---|---|
| **v1** | 按脚本切段，取「最后一个汉字段」为译文 | **灾难性失败** | 日文行**同时含假名与汉字**，`乾いた土にそっと　雨粒が流れてく` 被切成两半 |

### 6.2 算法骨架（伪代码）

```
────────────────────────────────────────────────────────────
阶段 A：清洗（在剥离时间戳之后！）
────────────────────────────────────────────────────────────
clean(line):
    b = stripTimestamps(line)            # 去掉全部 [mm:ss.xxx] 前缀
    b = removeInlineTags(b)              # 去掉行内 [tag:value]（含 [by:]、[ar:]…）
    if b 为空 or 命中制作人员模式(作词/作曲/编曲/歌/原曲/発売日/収録/…) → 丢弃
    return b
# 陷阱：必须先剥时间戳再滤元数据，否则 [00:00.000][by:xxx] 会漏过过滤（proto2 实测 bug）

────────────────────────────────────────────────────────────
阶段 B：语言类判定
────────────────────────────────────────────────────────────
classOf(cp):
    假名(平/片/半角片) → 'JA'           # 日文的决定性特征
    Han(含々〆〇)       → 'HAN'          # 中日共享，单独不足
    谚文              → 'KO'           # 韩文的决定性特征
    拉丁/西里尔/…      → 'LATN'/'CYRL'
    其他(空白/标点/分隔符/数字) → None   # 中性，黏附相邻强段

────────────────────────────────────────────────────────────
阶段 C：候选切点枚举 + 双向验证
────────────────────────────────────────────────────────────
candidates(text) =
    强分隔符位置    (' / ', '｜', '|', '／', '/')   # 作者显式意图；/'/' 也在其中（见 §6.2.2）
  ∪ 弱边界位置      ('\t', '　', ' ')             # 空白类：多为排版间距，需强证据
  ∪ 脚本过渡位置    (非目标强段 → 目标段)          # 无分隔符场景
  ∪ 括号区起点      (最外层配对括号区)             # 译文常被「」/（）整体包裹

trimEdges(text, cut, kind):
    # 只剥离【被匹配到的那个】分隔符 + 空白。
    # 不可剥离「所有分隔符」——`＼なので～す／ / ＼的~说／` 里作为内容的 `／` 会被误删。
    # kind 为 None（SCRIPT/括号路径）时改剥切点处残留的分隔类字符 ('/','／','|','｜')。

validateLoose(text, cut):               # 用于强分隔符与括号区
    左右非空即可
    （**不要求脚本证据**：强分隔符是作者的显式表态，见 §6.2.2）

validateStrict(text, cut):              # 用于弱边界（空白）
    (l, r) = trimEdges(text, cut)
    if l 空 or r 空 → 拒绝
    if profile(r)[HAN] == 0 → 拒绝
    if profile(r) 含任何 {JA, LATN, KO, CYRL} → 拒绝   # 右侧必须是【纯】目标语言
    if profile(l) 不含任何 {JA, LATN, KO, CYRL} → 拒绝 # 左侧须有「另一种语言」的决定性证据
    return (l, r)

# 两套验证的用途不同，不可混用：
#   宽松版  用于强分隔符与括号区（结构证据本身已足够）
#   严格版  用于弱边界——空白不携带任何意图，仅凭「右侧含目标语言」不足以确认
#           切点，原件一侧的空格同样会满足。

────────────────────────────────────────────────────────────
阶段 D：歌曲级约定推断（★ 本方案的核心）
────────────────────────────────────────────────────────────
inferConvention(lines):
    votes = 每个候选类型【存在任一通过验证的位置】的行数
    for kind in [' / ', '｜', '|', '／', '\t', '　', ' ', 'SCRIPT']:   # 优先级顺序
        if votes[kind] >= 2 and votes[kind] / len(lines) >= 0.4:
            return kind
    return None          # 无法确定 → 整首不切分

────────────────────────────────────────────────────────────
阶段 E：逐行应用（★ 受理条件随约定而变，不可统一成一套判据）
────────────────────────────────────────────────────────────
splitLine(text, convention):
    if convention 是强分隔符:
        if 该分隔符出现次数 >= 2 → 拒绝         # 多段并列，结构歧义（见 §6.2.3）
        for pos in 强分隔符位置 从右往左:         # 作者显式意图 → 取最后一个（D5）
            if validateLoose(text, pos) 通过 → return
        return 拒绝                              # **不回退**到括号/空白猜测
    if convention 是弱边界 或 SCRIPT:
        if 行内含 ' / ' 且 validateLoose 通过 → return   # 行内显式证据 > 文件弱约定
        if 存在 isTrailingBracket 的括号区 s:
            if 括号内容目标语言占比 >= 0.5 and validateLoose(text, s) 通过 → return
        if convention 是弱边界:
            for pos in 该类型位置 从【左】往右:   # ★ 见 §6.2.1
                if validateStrict(text, pos) 通过 → return
        else:
            if validateLoose 于脚本过渡点 通过 → return
    for s in 全部最外层括号区 从右往左:
        if 括号内容目标语言占比 >= 0.5 and validateLoose(text, s) 通过 → return
    return 拒绝              # 保守放弃：整行作原文
```

### 6.2.1 ★ 修正：「取最右」的假设是错的（原型 → 工具阶段的重大发现）

**§6.2 阶段 E 最初被实现为统一的「从后往前取最后一个通过验证的切点」**。这个假设在强分隔符上成立（D5：译文取最后一段），但**在弱边界上系统性错误**，并且原型阶段没有发现它——因为原型主要在 ` / ` 语料上度量。

**缺陷机理**：译文本身可能包含空白（`虽然不甘但还是喜欢你 这份纯情`）。取最右切点会落进译文内部：

```
行      : 悔しいけど好きって純情 虽然不甘但还是喜欢你 这份纯情
错误(最右): 原文=悔しいけど好きって純情 虽然不甘但还是喜欢你   译文=这份纯情
正确(最左): 原文=悔しいけど好きって純情                     译文=虽然不甘但还是喜欢你 这份纯情
```

**为什么「最左 + 严格版验证」才正确**：译文是**行尾那一段连续的目标语言区**，所以正确切点是「右侧成为合法目标语言区的**第一个**位置」——即该区的起点。配合 `validateStrict`（右侧必须纯目标语言），原语言一侧的空格会被自动跳过（其右侧含非目标类），从而精确落在语言类发生转换之处。

**客观实验（人工 ` / ` 边界为 ground truth，109,934 条）**

把每条已有人工 ` / ` 的行**替换为单个空格**（模拟弱约定），看哪种规则能还原人工边界：

| 扫描方向 | 还原正确 | 还原错误 | 准确率 |
|---|---|---|---|
| **最右（原实现）** | 78,634 | 29,193 | **72.93%** |
| **最左 + 严格验证** | 104,008 | 1,381 | **98.69%** |
| 最左 + 严格验证 + 括号兜底（占比≥0.5） | 104,065 | 1,533 | **98.55%** |

**这是 +25.6 个百分点的修正**，且全部来自扫描方向这一个变量。

**为什么必须保留「括号区起点优先于空白」**：译文可能内含拉丁词，使「右侧纯目标语言」不成立，此时只有括号结构能指出切点：

```
行    : Wee paks ra … enter FRELIA. 「我将开始歌唱诗歌『METAFALICA』 经由SOL=FAGE 与芙蕾莉亚共享意识」
括号优先: 原文=Wee paks ra … enter FRELIA.       译文=「我将开始歌唱诗歌『METAFALICA』 经由SOL=FAGE 与芙蕾莉亚共享意识」  ✓
空白优先: 原文=…FRELIA. 「我将开始歌唱诗歌『METAFALICA』 经由SOL=FAGE   译文=与芙蕾莉亚共享意识」              ✗
```

**且必须是「延伸到行尾的」括号区**，否则会把日文原文里的注音括号当作译文容器：

```
行: 高架橋（こうかきょう） 雨（あめ）降（ふ）らす神様（かみさま / ）/高架橋 降雨之神
    → `（こうかきょう）`/`（あめ）`/`（かみさま / ）` 都不延伸到行尾，不参与括号优先  ✓
```

**真实弱约定文件上的对照**（5,738 行，括号优先 vs 空白优先）：切分数相同（5,467），**括号内部误切 5 vs 16**，且全部 8 个差异样例都倾向括号优先：

```
行: 繫がるの 真向いの熱が 今 「现在，正面的热情正紧密相连」
  括号优先: 原文=繫がるの 真向いの熱が 今   译文=「现在，正面的热情正紧密相连」   ✓
  空白优先: 原文=繫がるの 真向いの熱が     译文=今 「现在，正面的热情正紧密相连」  ✗（`今` 应属原文）
```

**强分隔符上不可退到括号兜底**：若作者已写出 ` / ` 但该行验证不过（如译文同样含假名），应整行作原文（D10）。否则会用结构性猜测覆盖作者的**显式**意图，把「不确定」变成「确定的错」——实测该退化会让不一致数由 98 升到 105。

### 6.2.2 ★ 修正二：强分隔符**不可**要求脚本证据（用户第二轮复核）

用户第二轮复核了 120 条（`review-annotated-round2-2026-09-19.md`），其中 **109 条（91%）** 归为同一问题：

| 判定 | 条数 | 含义 |
|---|---|---|
| `错误，\`/\`左侧为日文，右侧为译文` | 39 + 37 | 算法**没切**（应切） |
| `错误，原文多了\`/\`` | 33 | 算法切了但**把 `/` 留在了原文** |

由此定位两个缺陷：

**缺陷 A —— 半角 `/`（不带空格）不是候选分隔符。** 相当数量的歌词直接写 `惚れた腫れたの馬鹿騒ぎ/愛意被潑冷水的超蠢騷動`，而算法只认带空格的 `" / "`，于是：
- 该文件推断出的约定是 `SCRIPT`（因为 `/` 不在候选里），走脚本过渡路径；
- 脚本过渡切点落在 `愛` 上，`/` 被留在原文里 —— 正是「原文多了 `/`」的成因。

修正：把 `/` 加入强分隔符候选与约定推断，**优先级低于** `" / "`（由歌曲级约定决定该文件用哪一种）。

**缺陷 B —— 强分隔符被过度验证。** 原 `validate` 要求「左侧必须有另一种语言的决定性证据」，而这一条是**专为弱边界设计的**；用到强分隔符上就会拒绝掉大量**真实存在**的切分：

```
言葉 / 这句话      ← 左「言葉」是日语汉字词，右「这句话」是简体中文，两侧脚本同为 HAN
矛盾 / 这矛盾        原验证要求左侧含 {JA,LATN,KO,CYRL}，纯汉字不满足 → 被拒
一途 / 这执着
```

用户判定这些**应当切分**。**这直接推翻了我此前「原理性盲区」的结论**：这些行的作者已经用分隔符明确写出了切分位置，脚本证据在此**不应成为门槛**。修正为：强分隔符只要求「两侧非空」，不再要求脚本证据。

**修正后实测收益**

|---|---|---|
| 与人工边界一致 | 107,619（97.89%） | **109,855（99.93%）** |
| 不一致 | 98（0.09%） | **2（0.00%）** → 后续三轮修复后 **0（§6.2.5、§6.6）** |
| 保守放弃 | 2,217（2.02%） | **77（0.07%）** |

### 6.2.3 新增守卫一：一行多个分隔符 → 放弃（D10）

强分隔符被采信后，出现一个新风险：**多段并列行**会被误当「原文 / 译文」。例如 `05 METHOD_MESSELA-.lrc` 的这一行（13 个 ` / `，用户判定「不切分是对的」）：

```
/ [我们呼应神子] / [欢欣鼓舞地咏唱诗] / … / [以制裁！] / [喜悦振奋地化为诗]
```

这是「以 `/` 分隔的多个中文片段」，不存在原文/译文对；按 D5 取最右切点会得到一个随机的两半。

**守卫**：一行内该分隔符出现次数 ≥ 2 → 整行作原文。全库仅 **71 行（0.065%）** 命中，且这些行本身结构就歧义（`原文A / 原文B / 译文A / 译文B`），人类标注自己也只取「第一个 ` / `」，放弃比赌更符合 D10。

### 6.2.4 新增守卫二：弱约定路径只尝试带空格的 ` / `（踩坑记录）

为修 §6.2.2 的另一类错误（`11. 花のように.lrc` 的约定是空白，但个别行写着 `唄：花たん（ユリカ） / 演唱：花たん（百合香）`，被弱约定路径的括号优先切成 `…演唱：花たん` / `（百合香）`），让弱约定路径**先尝试行内 ` / `**——行内显式证据强于文件的弱约定。

**但第一版把「全部强分隔符」都试了，立刻引入回归**：

```
行: Wee paks ra … SOL_FAGE/1x10 enter FRELIA. 「我将开始歌唱诗歌…」
错: 切在 `SOL_FAGE/1x10` 的裸 `/` 上      ← 那是原文记法，不是分隔符
对: 切在 `「` 之前（括号路径）
```

**修正**：弱约定路径**只尝试带空格的 ` / `**。理由：裸 `/` 若真是该文件的约定，约定推断会给出 `"/"` 并走强分隔符路径；而只在个别行出现的裸 `/` 更可能是原文记法。

> 这两次修正共触及 3 个新缺陷（`/` 缺失、过度验证、多段并列），全部由用户的两轮人工复核定位。**这是 P3 复核机制最直接的收益证明。**

### 6.2.5 新增守卫三：显式 ` / ` 存在时禁用「延伸到行尾的括号区」猜测（最后一处回归的根因）

§6.2.4 的修正落地后，全库不一致从 2 条降到 0 —— 但那 **2 条**的根因与 §6.2.4 无关，是另一个独立缺陷，值得单独记录，因为它体现了本算法的核心优先级原则。

**现象**（`11. 花のように.lrc`，约定为空白）：

```
行: 「A」 / 「B」 / 「C」 / 「B」        （A=日文原文, B/C=繁/简中译文）
人工: 原文=「A」   译文=「B」 / 「C」 / 「B」
算法: 原文=「A」 / 「B」 / 「C」 /     译文=「B」      ← 原文被污染
```

**根因**：该行含 3 个 ` / `，触发 §6.2.3 的多分隔符守卫 → `_cut_explicit` 返回 None → 代码继续走到**「延伸到行尾的括号区」**路径。该路径发现行尾是 `「B」`（配对括号且延伸到行尾、内容以目标语言为主），于是把它的**起点**当切点 —— 但那是**第 4 段**的起点，于是前 3 段全部落进原文。

**修正**：行内已含显式 ` / ` 时，**不再**走括号结构猜测，直接交给下面的弱边界路径（它会取最左的、右侧纯目标的切点，正好落在 `「A」` 之后）。

**为什么这条原则重要**：括号区起点**只是结构线索**（「译文常被括号包裹」的排版观察），而 ` / ` 是**作者的显式表态**。两者冲突时必须让显式证据胜出 —— 与 §6.2.2（强分隔符不要求脚本证据）、§6.2.4（行内 ` / ` 强于文件弱约定）同属一条原则：**显式结构 > 结构性猜测**。

> 这也是**最后一处**实证回归。修正后全库 109,857 行对照**零不一致**（§6.6）。

##### 缺陷 13：强分隔符全在括号内 ⇒ 该行其实没有分隔符，却仍被整行作原文

用户判错的两行同属 `05. Sound Horizon — 檻の中の遊戯.lrc`：

```
蔷薇を想わせる绯色の『口红』(ローズレッドルージュ / )  令人联想起玫瑰的绯色口红
あの『悲鸣は』(うたごえが / )『葡萄酒』   那悲鸣（歌声）有如葡萄美酒
```

两行的 `/` 都在**注音括号内部**（读音装饰），真正的分界是括号后的**空白**。文件约定是 ` / `，于是走强分支；强分支发现候选全在括号内，试了「括号外其它强分隔符」与「括号区起点」都失败，**直接返回整行原文**——从未尝试弱边界。

**修复**：强分支的括号内降级链末尾追加**弱边界（合并三种空白，按位置升序取最左）→ SCRIPT**。判据仍是 D28 的「左侧非目标语言 → 右侧为目标语言」。

> **与 D10 不冲突，二者边界必须说清**：D10「强分隔符验证不过则整行作原文」约束的是候选**在括号外**却被否决的行（那类行的 `/` 是真分隔符，只是分段过多，实测 **53 行**，仍整行作原文）；本次是候选**全部**在括号内，证明它们不是分隔符而是读音装饰，故不构成「作者已表态」。
> 全库仅 **5 行**满足「候选全在括号内」：**2 行修好**（即用户标注的两行，输出与用户期望**逐字节一致**）、**3 行仍拒绝**、**0 行附带影响**。

**★ 同期测量并否决的更大改动**：把兜底放宽到「行内**根本没有**强分隔符」的情形（Case A，**1173 行**）。实测会让 98 行从「整行原文」变为「切分」，但样例**绝大多数是错的**——全是制作人员行（`編曲：コンプ，kaztora，津久井龍馬`）、标题（`一番の宝物` → `一番の`/`宝物`）、日文行（`私を呼んでいるのは誰？`）。**用户自己的标注也否证了它**：本轮 14 条 `validate-failed` 标注中 **12 条判「正确」**（`四月是你的谎言ED2`、`词曲：MICHIRU`、`終わり` 等，即拒绝是对的），只有 2 条判「错误」。故**不放宽**。

##### 缺陷 14：反斜杠 `\` 作分隔符的文件被整体切错

用户把 `水樹奈々 - リプレイマシン.lrc` 整首判为「错误」。该文件**几乎每行**都用 `原文\译文`，而 `CONVENTIONS` 里没有 `\`，于是文件约定被推断成**空格**，导致：

* 含空格的行被**切在译文内部的空格上**，译文**只剩后半句**（`…背伸びしてもいい\回首也可以 成长也可以` → 译文 `成长也可以`）；
* 不含空格的行**整行无译文**（含用户点名的首行）。

**修复**：把 `\` 加入 `STRONG_SEPARATORS` **末位**（`infer_convention` 是「首个匹配即得票」，置末位保证正文里的反斜杠不抢走 ` / ` 的票）。效果：该文件约定 ` ` → `\`（31 票），**31 行全部修正**（译文修正 21 + 新增覆盖 10），用户点名的首行输出与期望**逐字节一致**；**全库只有这 1 个文件的约定发生变化**，其余 1615 个文件零影响。

> **同期测量并否决的两项**，都记录在此以免后人重犯：
> ① **把 `\` 也加进 `SEPARATOR_TRAIL_CHARS`**（即剥译文侧的反斜杠）：会毁掉作者的转义写法——` / \t人生中 大家都愚蠢地可爱` 里的 `\t` 是**制表符的转义**，一概剥离会变成 `t人生中…`，实测**破坏 131 行**。代价是 `…★／ / \放马过来！…/` 这类用反斜杠包住译文的行保留首尾装饰（**2 行，仅外观，边界本身正确**）。
> ② **新写「未知分隔符」探测器**（文件级：未知 ASCII 标点出现在 ≥40% 行且左非目标/右目标）：实测**噪声 72 个文件**（`.`, `)`, `,`, `?`, `!`, `:`, `;` 全是正文标点）；**「原文以目标语言串结尾」启发式**更差，**55 条命中 55 条误报**（日语原文合法地以汉字结尾，与中文同类）。故**不加**，转而诚实披露盲区（下条）。

## 7. 最优方案

### 7.1 方案选型

| 方案 | 精度 | 依赖 | 跨平台 | 优雅度 | 结论 |
|---|---|---|---|---|---|
| **A. 纯 ICU 脚本连段 + 双向验证 + 歌曲级约定推断** | **判定精确率 100.00%（不一致 0 / 109,857 行）**；弱约定覆盖率 96.9%、客观缺陷 11 行（§6.6） | **0（ICU 已在）** | Win/Linux/macOS 全覆盖 | 高（约 200 行纯函数） | ✅ **采用** |
| B. A + CLD3 兜底（仅纯汉字歧义时） | 提升有限 | vcpkg `cld3` + 须重配 140 字节下限 | 三端可供给 | 中 | ❌ 短句超出其设计工况，收益不抵复杂度 |
| C. A + fastText | — | 917KB 模型 + CC-BY-SA 模型许可 + 无 vcpkg/brew | 手工三端 | 低 | ❌ |
| D. lingua（Rust FFI） | 宣称最优 | ~300MB + Rust 工具链 + 无官方 C ABI | 最重 | 低 | ❌ |
| E. libexttextcat | 差（实测中文→日文误判，Wili-2018 仅 ~30%） | 190 个模型 | Linux 常见 | 低 | ❌ **排除** |
| F. 保留用户分隔符配置 | — | 0 | — | **低（正是被否定的现状）** | ❌ |

**采用方案 A**，理由：①**零新增依赖**（ICU 已是后端既有依赖，且本算法只用 `uscript_getScript`，甚至可不用 ICU 的 `i18n` 组件）；②**精度最高**（实测 99.97%）；③**跨平台天然可行**（无模型文件、无 Rust、无 vcpkg port 缺口）；④**最优雅**（纯函数、无状态、可完整单测）；⑤**诚实的能力边界**（原理性盲区明确写为「不切分」）。

### 7.2 架构归属（用户已裁决：**后端**）+ 懒惰切分

依用户裁决「后端（与排序权威一致）」，且纠错表必须落在后端 DB。因此：

- **算法**：后端新模块 `src/control/lyric_split.{h,cpp}`，纯函数，无 I/O。
- **覆盖层**：后端新增专用表（内容寻址），在切分入口处先查覆盖、命中即直接返回，**不跑算法**（满足 R4）。
- **契约**：`LyricLine` 扩展出原文/译文与置信度（**破坏性变更**，用户已授权；下游 `find_package(SerionaBackend)` 消费者需成对重建）。
- **前端**：退化为渲染器 + 纠错 UI；删除 `m_lyricDelimiters` 与设置卡片。

**★ 懒惰切分（用户已裁决，D21）**

切分**不在扫描期**、也**不在建树期**进行，而是**只在用户播放该曲目时**才处理。由此得到三项设计后果：

| 后果 | 说明 |
|---|---|
| ① 切分时机 = 当前曲目快照构建时 | 库树中的 `effectiveLyrics` **保持原始 `text` 不变**（不切分、不冗余存储）；切分在构建 `PlayerStateSnapshot`（当前曲目）时施加。启动/扫描/建树**零额外成本**。 |
| ② 切分结果需要**带目标语言标记的缓存** | 用户明确要求「以存储这个结果的目标语言来判断该结果可用还是过时」。因此缓存**必须**记录产出它所依据的目标语言；`cachedLang != currentTargetLang` 即判为过时。 |
| ③ 目标语言变更**只影响已算过的曲目** | 已算过 → 废弃旧结果、重算；**从未算过 → 无需任何处理**（无结果即无过时问题）。整库无需遍历。 |

**缓存载体**：扩展现有 `lyrics` 表（`schema.sql:58-66`），新增 `original` / `translation` / `split_target_lang` 三列（**schema 版本升级** `user_version` 3 → 4）：

```sql
-- lyrics 表（既有）+ 新增列
original          TEXT,      -- 切分后的原文；NULL = 尚未切分
translation       TEXT,      -- 译文；NULL = 尚未切分（空串 = 已切分但无译文）
split_target_lang TEXT       -- 产出上述结果时使用的目标语言
```

**装载与失效逻辑**：

```
loadSplit(locationId, kind, lineIndex):
    row = SELECT text, original, translation, split_target_lang FROM lyrics ...
    if row.split_target_lang == currentTargetLang and row.original != NULL:
        return 缓存命中                     # 直接用，不跑算法
    return 未命中                            # 调用方触发切分并回写

# 目标语言变更：不遍历、不批量作废。
# 旧行因 split_target_lang 不匹配而自然失效；下次播放该曲时重算并覆盖。
```

**为何不采用「全库重算 + 重推」**（原 §13-Q2 的候选）：实测 122,241 行全量重算的耗时未测，且绝大多数曲目在一次会话中根本不会被播放 —— 懒惰切分把成本摊到实际使用上，启动与切换目标语言均为**零等待**。

**注意**：`location_id` 在文件 mtime/改名变化时会变，故该缓存天然是「按位置」的淘汰式缓存，与既有语义一致。

### 7.3 分层优先级（必须写进实现）

```
1. 内容寻址覆盖缓存（用户纠错）          ← 最高优先：命中即返回，不跑算法
2. 歌曲级约定推断结果
3. 强分隔符候选（ / 、｜、|、／）
4. 弱边界候选（Tab、全角空格、双空格、单空格）  ← 须由第 2 步背书
5. 脚本过渡候选（无分隔符场景）           ← 须由第 2 步背书
6. 保守放弃 → 整行作原文、译文为空
```

### 7.4 目标语言可配置（满足 R2 / F4 教训）

- 默认 `zh`。目标语言决定「目标语言类」是什么（`zh→HAN`、`ja→JA`、`ko→KO`、`en→LATN`）。
- **绝不**硬编码 `zh-Hans`（LyricsX F4 的教训）。
- 变更目标语言须触发重新切分 + 重推歌词（后端方案的代价，见 §9.2）。

### 7.5 内部扩展点（满足 R7）

译文位置在代码中抽象为**单一策略点**：

```
enum class TranslationPosition { LastLanguageSegment };   // 当前唯一实现
```

将来扩展为 `FirstLanguageSegment` / `NthSegment` / `ByLanguage` 时，只需在**该策略点**内改动，调用方与 UI 不变。**不暴露为任何用户设置**（用户裁决）。

**接口草案**（纯函数、无 I/O、可单测）：

```cpp
namespace seriona::control {

enum class LyricLanguage { Unknown, Han, Japanese, Korean, Latin, Cyrillic };

struct LyricSplitResult {
  std::string original;       // 原文（未切分时 = 整行）
  std::string translation;    // 译文；无译文时为空
  bool split{false};          // 是否成功切分
  double confidence{0.0};     // 0..1，用于 UI 提示与「需人工确认」排序
};

// 内部扩展点：译文位置策略（当前仅 LastLanguageSegment）
// 纯函数：同一输入必得同一输出（无 I/O、无状态、无随机）
[[nodiscard]] LyricSplitResult splitLyricLine(std::string_view line,
                                             std::string_view targetLanguage);

// 歌曲级约定（一次性推断，供整首复用）
enum class LyricSplitConvention { None, SlashSpaced, FullwidthBar, Bar, FullwidthSlash,
                                  Tab, FullwidthSpace, DoubleSpace, Space, ScriptTransition };
[[nodiscard]] LyricSplitConvention inferSplitConvention(
    const std::vector<std::string>& lines);

}  // namespace seriona::control
```

**核心实现要点**（对应 §6.2/§6.3）：

| 要点 | 实现 |
|---|---|
| 脚本查询 | `uscript_getScript(cp, &err)`；自写约 40 行 run 分割（可移植 ICU `extra/scrptrun` 的 `ParenStack` 思路） |
| 中性黏附 | `Common/Inherited/Unknown` 附着到前一个强 run |
| **括号配对** | 开括号 → 归属其后第一个强 run；闭括号 → 归属其前第一个强 run（**P3**） |
| 双向验证 | 右侧须含目标语言类且**不含**假名/谚文；左侧须含至少一个非目标决定性类 |
| 清洗顺序 | 先剥时间戳 → 再去行内 `[tag:value]` → 最后滤制作人员（**P1**） |
| 中文功能字表 | **逐字**声明（**P2**），禁止由词语拼接 |
| 可选：简化 | 若不想在 `control` 层引入 ICU，可用 `UCHAR_SCRIPT` 的 `u_getIntPropertyValue` 替代（`uchar.h`），仍属 ICU `uc` |

### 8.3 后端：纠错覆盖表（内容寻址）

**范式**：照搬 `folder_sort_rules`（专用 SQLite 表 + 手写序列化，无 JSON 库）。

```sql
CREATE TABLE IF NOT EXISTS lyric_split_overrides(
  text_hash      TEXT NOT NULL,     -- SHA-256(原文行文本) 的十六进制
  target_lang    TEXT NOT NULL,     -- 目标语言（如 'zh'）
  raw_text       TEXT NOT NULL,     -- 原始整行（便于管理列表展示、校验哈希）
  original       TEXT NOT NULL,     -- 用户指定的原文
  translation    TEXT NOT NULL,     -- 用户指定的译文（空串 = 显式「此行无译文」）
  updated_at_ms  INTEGER NOT NULL,
  PRIMARY KEY(text_hash, target_lang)
);
```

**为何用哈希而非原文作主键**：原文可达 200 字符，直接作复合主键浪费且索引臃肿；哈希定长、索引高效。**但必须同时存 `raw_text`**：①管理列表需要展示；②哈希碰撞时可比对校验；③避免只存哈希导致用户无法理解自己改了什么。

**覆盖语义**：

```
splitLineWithOverride(text, targetLang):
    h = sha256(text)
    if 命中 (h, targetLang):  return 覆盖值        ← 不跑算法（R4）
    else:                     return splitLyricLine(text, targetLang)
```

**「此行无译文」的表达**：`translation = ''` 且需与「未纠正」区分 → 因此**必须**有覆盖行存在（用 `original = text, translation = ''` 表示「整行原文、无译文」）。

**接口草案**（与 `FolderSortSettingsStore` 同形）：

```cpp
class LyricSplitOverrideStore {
  virtual void upsert(LyricSplitOverride) = 0;
  [[nodiscard]] virtual std::optional<LyricSplitOverride> load(
      std::string_view textHash, std::string_view targetLang) const = 0;
  virtual void remove(std::string_view textHash, std::string_view targetLang) = 0;
  [[nodiscard]] virtual std::vector<LyricSplitOverride> list() const = 0;   // 管理列表
```

**批量查询优化**：一首歌最多数百行，逐行查 DB 会有 N 次往返。建议**一次载入整表到内存映射**（纠错条数天然很少，用户手工产物），或提供 `loadMany(hashes)` 批量接口。

### 8.8 同时间戳双行（参照行）支持（用户已裁决 D22：纳入本次范围）

依 §5.2 形态 A2，ESLyric 官方 wiki 定义的约定是：

> 相同时间戳的歌词行将视作拥有参照的歌词行，其中**第一行将作为原始歌词** … 同一时间戳的参照歌词按序显示，**不要求为连续行**

**★ 必须先修的阻塞项（本次调研新发现，当前实现会静默破坏该约定）**

后端 `src/scanner/lrc_parser.cpp:165-171` 与 TagReader `src/text/TextNormalize.cpp:225-235` **都按 `(timestamp, text)` 排序，且均为非稳定排序**：

```cpp
// lrc_parser.cpp:165-171
std::ranges::sort(result.lines, [](const LyricLine& lhs, const LyricLine& rhs) {
  if (lhs.timestamp != rhs.timestamp) return lhs.timestamp < rhs.timestamp;
  return lhs.text < rhs.text;              // ← 同时间戳行被按文本重排
});

// TextNormalize.cpp:225-233（TagReader 内嵌歌词侧，同一问题）
std::sort(..., [](const auto &lhs, const auto &rhs) {
    if (lhs.first != rhs.first) return lhs.first < rhs.first;
    return lhs.second < rhs.second;        // ← 同时间戳行被按文本重排
});
```

`std::sort` / `std::ranges::sort` **不保证稳定**，因此同一时间戳的多行会被**按文本内容重新排列**。而参照行约定要求「**第一行** = 原文」，即**时间戳组内的文件原始顺序必须保留**。

**结论**：实现 A2 的**前置条件**是把两处排序都改为**只按 `timestamp` 的稳定排序**（`std::stable_sort`，或按时间戳比较且不比较文本），从而保留同时间戳组内的文件顺序。**否则该特性会在运行时静默产出错误的原文/译文配对**，且难以察觉。

**实现要点**：

| 项 | 做法 |
|---|---|
| 排序 | 两处改为仅按 `timestamp` 的稳定排序（见上）；去重仍按 `(timestamp, text)` 但须在稳定排序后执行，避免误删同刻不同文本的行 |
| 配对规则 | 对同一 `timestamp` 的组：第 1 行 = 原文；第 2..n 行 = 译文（多行译文按序合并，或用换行拼接）。若组内第 1 行本身就是空白/占位则跳过 |
| 「不要求为连续行」 | ESLyric 明确允许参照行不相邻 → 配对必须**按时间戳分组**，**不得**依赖行相邻（`Tick` 的分组必须用 map/分组，而不是「看上一行」） |
| 与行内切分的交互 | 若组内第 1 行**本身**又含行内分隔符，则**先做行内切分，再**考虑参照行；或明确「同一首歌不同时使用两种约定」并给出优先级（建议：行内切分为高优先，参照行为其补充） |
| 空行/占位（F2/F3 教训） | 参照行配对前必须已完成 §6.2 阶段 A 的清洗（剥时间戳 → 去行内 tag → 滤制作人员、滤空行），否则会重演 ESLyric #243 的空行误判 |
| 多时间戳行的交互（F3） | 一行带多个时间戳（副歌复用）时，ESLyric **静默失效**。本实现须明确定义：多时间戳展开后**每个时间戳各自成组**，参照行只作用于其所属时间戳组 |
| `「参照行」的置信度 | 由于第一行=原文是**约定**而非推断，此路径置信度可视为高；但若组内行数 >2 或文本重复，应降低并仍记录（内部使用） |

#### 8.9.1 G1 实施要点（`offset`）

`[offset:+ms]` 的语义是**毫秒**，正数=歌词**提前**显示（即时间戳需**减去** offset），负数相反。实施要求：

- 标签可出现在文件**任意位置**（多在头部，但规范未强制），因此需**两遍解析**：先扫出 offset，再生成时间戳；或先收集再统一加减。
- offset 与 `[ti:]` 等一样是**单值**语义，若出现多次，按 LRC 惯例**后者覆盖前者**（AIMP/Walaoke 行为一致）。
- 应用后若出现**负时间戳**，钳到 0（而不是丢弃该行）。

#### 8.9.2 G2 实施要点（稳定排序）

两处（`lrc_parser.cpp` 与 `TextNormalize.cpp`）都必须改为**按时间戳稳定排序**：

- 稳定排序后，**同一时间戳的两行保持文件中出现的先后顺序**——这正是 D22 参照行约定的前提（第一行 = 原文，第二行 = 译文）。
- 不可用 `std::sort`（不稳定）；用 `std::stable_sort`。仅按 timestamp 比较，**不再把 text 作为次级键**（把 text 作为次级键正是当前的缺陷根源）。
- 两处必须同时改：LRC 文件侧与内嵌标签（ID3 USLT/SYLT 等）侧走的是不同代码路径，只改一处会让两种来源的排序行为不一致。

#### 8.9.3 G3 实施要点（增强 LRC 逐字标签）

`<mm:ss.xx>` 的语义是**该字符的起始时间**。对本次功能而言：

- **必须从显示的歌词文本中剥离**（否则用户看到字面量）。
- 剥离后，一行的多个字符时间被**丢弃**，整行沿用其行首时间戳。逐字高亮（karaoke 效果）**不在本次范围**。
- **注意与「比较运算」的歧义**：歌词正文里可能出现 `<`（如 `a < b`）。仅当 `<` 后**严格匹配** `mm:ss.xx` 或 `mm:ss.xxx` 形态时才当标签处理。

#### 8.9.4 G4 实施要点（unsynced 歌词）

现状是「无 `[...]` 的行 → `continue`」，导致纯文本 `.lrc` 整首消失。修正为：

- **整首无任何时间戳** → 视为 unsynced 歌词：**保留全部行**，时间戳置为 0（或标记为 unsynced）。
- **混合形态**（部分行有时间戳）→ 保持现状丢弃无时间戳行（这类行通常是文件尾部的制作者署名，而非歌词）。
- 这与 G6「行内元数据丢弃」是**两条不同路径**：G6 丢弃的是**标签**，G4 保留的是**正文**。

#### 8.9.5 G5 实施要点（格式范围）

按「本地播放器」定位（P4）与本功能的相关性，**分三档**处理：

| 档 | 格式 | 处理 |
|---|---|---|
| **纳入** | `.lrc`（含增强/unsynced）、`.txt`（同 unsynced 处理） | 直接实现；`.txt` 的判定需**内容嗅探**（见下） |
| **纳入（新解析器）** | `.srt`、`.ass`、`.ttml` | `.srt`：序号块 + `hh:mm:ss,mmm --> hh:mm:ss,mmm` + 文本；`.ass`：`[Events]` 段的 `Dialogue:` 行（**须剥离 `{\...}` 特效/定位标签**）；`.ttml`：XML，取 `<p begin="..">`（**若含 `<translation>` 轨道，可作译文的额外来源**——但这与 D5/D6 的「行内分段」是不同机制，**本次不进算法，仅解析后作为独立行交给算法**） |
| **不纳入** | `.krc`（酷狗）、`.qrc`（QQ）、`.yrc`（网易云逐字） | 私有/加密格式，无公开规范，工程量与法律风险都不成比例；**在代码中注释说明为何不纳入**，避免后人误以为遗漏 |

`.txt` 判定的**内容嗅探**要求：扩展名是 `.txt` 时，须确认内容**至少包含一个**合法时间戳标签或**整首无标签但确有文本**，且**排除**常见纯文本（README、`desktop.ini` 等）——否则会把曲库里任意 `.txt` 当歌词。建议的保守判据：文件 ≤ 某尺寸上限 **且**（含 `[mm:ss]` **或** 不含任何 `[` 且行数 ≤ 200）。

> **测试面**：G5 新增三种解析器，每种都需要独立的字节级测试（编码、CRLF、空行、BOM）。这是本次**工程量最大**的一项。


### 8.10 旧库拒绝路径（D26 已裁决；**消息清晰化经 P8 裁决纳入本次范围**）

用户要求：不做迁移，旧库在点击「恢复播放列表」时直接拒绝。

**现有机制（已核实）**：`SQLiteCache::open()` 在 `user_version != kSchemaVersion` 时 `throw std::runtime_error("unsupported scanner cache schema version")`。把 `kSchemaVersion` 由 3 改为 4 即触发拒绝——**这正是 D26 所需**。

**但实际链路存在两处问题**（本次核实新发现）：

1. **异常在启动期就被吞掉**：控制器经 `BackendBridge::ensureStarted()` 惰性创建，该函数用**无信息量的裸 `catch (...)`** 捕获并直接 `return`，且置 `m_shuttingDown = true`：
   ```cpp
   } catch (...) {
       m_shuttingDown = true;
       unsubscribeAll();
       if (m_controller) { m_controller->shutdown(); m_controller.reset(); }
       return;                     // ← 失败原因被丢弃
   }
   ```
2. **用户看到的消息与真实原因无关**：点击「恢复播放列表」→ `scanLibrary()` 的守卫 `if (m_shuttingDown || !m_controller)` 命中 → 返回 `controllerStoppedResult()`，其消息是 **`"Media controller is stopped"`**。前端据此 `setScanStatus("error")` + `setLastError(...)`，用户在 StartupView 看到的是**「播放控制器已停止」**，而非「数据库版本不兼容，请重新扫描曲库」。

**裁决（P8）：纳入**。理由：D26 的功能要求虽天然满足（确实被拒绝、不会崩溃、不会损坏数据），但用户**无法理解发生了什么，也无从知道该怎么办**——一个无法自救的错误提示等于没做拒绝。跨前后端约 4 处小改动，成本可控。

| 改动 | 位置 | 说明 |
|---|---|---|
| 让 schema 不兼容可被识别 | `SQLiteCache::open()` | 抛出**专用异常类型**（如 `SchemaVersionMismatch`）而非泛化 `runtime_error`，携带 `found` / `expected` 版本号 |
| 不再吞掉原因 | `BackendBridge::ensureStarted()` | 捕获该专用异常并**缓存其消息**，供后续命令返回；其余异常仍走原路径（不得让所有异常都冒充「版本不兼容」） |
| 返回有意义的结果 | `BackendBridge::scanLibrary()` | 命中不可启动状态时返回带**具体原因**的 `MediaControllerCommandResult`，而非泛化的 `controllerStoppedResult()` |
| 前端呈现 | `LibraryController::requestScanForRoot()` | 已有 `setLastError(result.message)` 通路，只要消息正确即可自动展示 |

**消息文案要求**（面向用户，须可操作）：

- 必须说明**是什么**：本地数据由旧版本创建，当前版本无法读取。
- 必须说明**怎么办**：请在设置中「重新扫描曲库」以重建（本定位下重建成本可接受——只会重扫元数据，不损失音频文件与用户对文件本身的改动）。
- **禁止**出现 `unsupported scanner cache schema version` 这类内部英文串，也**禁止**沿用 `"Media controller is stopped"`（该消息指示的是完全不同的故障，会误导排查方向）。

**边界约束**：该专用异常**不得**被用于掩盖其它启动失败（端口占用、DLL 缺失等）。实现上应只在 `SQLiteCache::open()` 抛出该类型时走这条路径，其它异常保持原有行为并同样**记录**（不得继续静默吞掉——这是本次顺带修正的既有问题）。

## 11. 备选方案（未采用，保留备查）

### 11.1 前端算法 + 后端持久化（更轻，未采用）

- 前端新增 `LyricSplitter`（用 Qt 自带 `QChar::script()`，**无需 ICU**）；纠错表仍在后端 DB，前端启动拉取全量覆盖映射并本地查表。

- **未采用原因**：用户裁决后端，以与刚确立的「后端唯一权威」架构一致。
- **保留价值**：若后端方案的「目标语言变更重推」被证明代价过高，可退回此方案，且算法设计（§6）可**原样复用**。

### 11.2 同时存储独立字段（生态正解，但**本次确定不做**）

- 生态的正解是「译文作为独立字段/轨道传递」（§5.3）。若将来支持从 API 获取歌词（网易云 `tlyric`、QQ `trans`、TTML `<translation>`），应**优先使用独立字段**，把内联切分降为兜底。
- **但用户已裁决（D27）：不接入网易云等外部 API，播放器定位为本地播放器。** 因此本方案**不预留**「译文来源」维度，也不实现独立字段通路。数据源就是本地 `.lrc` sidecar 与内嵌标签，**内联切分即是唯一路径**（不是兜底）。
- 若未来产品定位改变，再按本节思路扩展。

见 §5.7。唯一可行的折中是「CLD3 + 重配 `min_num_bytes` + 限定 `{zh,ja}` 语言集 + 长度门限」，仅在「纯汉字且 ≥N 字」时调用。**本方案不采用**，但若将来盲区被证明不可接受，可作为**纯汉字盲区**的可选补充（不参与主干）。

## 附录 C：术语表

| 术语 | 含义 |
|---|---|
| **script run（脚本连段）** | 把字符串按 Unicode `Script` 属性切成连续同类段 |
| **决定性特征** | 能唯一确定语言的字符：假名⇒日文、谚文⇒韩文；汉字**不是**决定性特征 |
| **双向验证** | 切点须同时满足「右侧=目标语言且无假名/谚文」与「左侧含另一种语言的决定性证据」 |
| **强/弱分隔符** | 强：` / `、`｜`、`\|`、`／`（作者显式意图）；弱：空白类（多为排版间距，须整首一致性背书） |
| **歌曲级约定推断** | 从整首歌词的聚合证据推断本文件采用的切分约定，再逐行应用（本方案核心） |
| **内容寻址覆盖** | 纠错以「原文文本 + 目标语言」为键存储，同一输入在任意曲目/位置均复用该纠正 |
| **塔语（Hymmnos）** | 《魔塔大陆》系列的人造语言；罗马字转写 Script = Latin，任何 LID 都无法识别 |
